# ADR 0007: 시간 모델 — 시뮬레이션 틱, 하루, 계절

- 상태: 확정 (2026-11-28, 2단계 시작 전 정리)
- 관련: [ADR 0002](0002-architecture.md) (결정론적 코어), [ADR 0004](0004-traffic-model.md) (이벤트 기반 교통), [game-loop.md](../design/game-loop.md), [balance.md](../design/balance.md)

## 문제

기획 문서(game-loop.md)는 "틱 = 1분(게임 내)"이라고 했지만, 1단계 코어는 **틱 = 100 ms 시뮬레이션 시간**으로 만들어졌습니다(`TICK_MS = 100`). 교통은 틱마다 계산하지 않고 정수 ms 이벤트로 처리하므로, 틱은 "명령을 적용하고 이벤트를 어디까지 처리할지 정하는 경계"일 뿐입니다. 두 정의가 섞이면 2단계(인구·경제·기후)의 갱신 주기와 플레이 속도를 정할 수 없습니다.

## 결정

| 개념 | 정의 | 어디에 |
| --- | --- | --- |
| **시뮬레이션 시각** | 정수 밀리초(ms), 자정 = 0. 모든 이벤트·기록의 시간축 | 코어 |
| **틱** | 100 ms. 명령 적용과 이벤트 처리의 경계. `step(n)` = n × 100 ms | 코어 (`TICK_MS`) |
| **게임 내 분** | 600틱 = 60,000 ms. 화면 시계·기획 문서에서 쓰는 단위 | 문서·UI |
| **하루** | 864,000틱 = 86,400,000 ms. 시민 일과(통근 등), 일 최고기온 | 코어·문서 |
| **계절** | 90일. 플레이어 결정 주기, 예산 집행 | 2단계 코어 |
| **년** | 4계절 | 2단계 코어 |
| **재생 속도** | 클라이언트가 실시간 1초에 진행하는 시뮬레이션 초 (지금 1~300배) | 클라이언트 |

1. 코어의 틱은 **100 ms로 고정**합니다. 게임 내 시간 단위는 틱이 아니라 시뮬레이션 시각(ms)으로 말합니다. "틱 = 1분"이라는 표현은 쓰지 않습니다.
2. 갱신 주기가 다른 모델은 **시뮬레이션 시각 기준 이벤트**로 붙입니다: 교통은 ms 이벤트(지금처럼), 폭염·침수 격자는 게임 내 1분~10분 간격 이벤트, 인구·경제는 하루·계절 경계 이벤트. 이들 간격은 각 모델 이슈에서 정하고 근거를 남깁니다.
3. **계절 진행은 대표일 방식**으로 합니다. 90일을 매일 차량 단위로 돌리지 않고, 계절마다 **대표 평일 하루**를 차량 단위로 돌려 지표(평균 통근 시간 등)를 얻고, 기후 사건이 있는 날은 그날을 따로 돌립니다. 하루 단위 집계(인구·세수 등)는 90일을 곱하거나 일별 간단 모델로 계산합니다.
4. 플레이어가 "빨리 감기"로 보는 화면은 대표일을 재생 속도로 보여 주는 것입니다. 결정론은 그대로입니다(같은 입력·시드 → 같은 대표일 결과).

## 이유

- 100 ms 틱은 이미 교통·명령·Python·Godot 바인딩과 테스트(결정론 포함)에 쓰이고 있고, 이벤트 기반이라 틱이 짧아도 비용이 거의 늘지 않습니다. 1분 틱으로 바꾸면 명령 반응이 1분 단위로 거칠어지고 얻는 것이 없습니다.
- 평택역 맵 출퇴근 하루(통행 3,380개)는 debug 빌드에서 약 4~8초가 걸립니다([balance.md](../design/balance.md) 실험). 계절(90일)을 매일 돌리면 수 분~수십 분이 걸려 "계절마다 결정"하는 루프(game-loop.md)에 맞지 않습니다. 대표일 방식이면 계절 진행이 대표일 몇 개 비용으로 끝납니다.
- 교통 지표는 같은 구역·도로·정책이면 평일마다 거의 같습니다(수요 모델이 결정론적이고, 요일 차이가 아직 없음). 그래서 대표일 하나로 계절 평균을 대신해도 1·2단계 목표("정책을 바꾸면 통근 시간이 어떻게 바뀌나")에 충분합니다.

## 검토한 대안

- **코어 틱을 1분으로 바꿈**: 교통 이벤트를 분 단위로 뭉개야 하고, 1단계 테스트·밸런스 수치가 모두 바뀜. 이득 없음.
- **계절 90일을 매일 전부 시뮬레이션**: 가장 정직하지만 계산 비용이 너무 큼. 요일·계절 변동 모델이 생기면 "대표일 여러 개(평일·주말·사건일)"로 늘리는 방향으로 검토.
- **틱 길이를 설정값으로 둠**: 결정론 테스트와 저장 파일 호환성이 틱 길이에 묶여 복잡해짐. 고정값으로 둠.

## 결과

- game-loop.md의 시간 단위 표를 이 정의로 바꿉니다.
- 2단계 이슈(인구·경제·기후)는 갱신 주기를 "시뮬레이션 시각 기준 이벤트(분·하루·계절)"로 정의합니다.
- 계절 진행 API(대표일 실행, 계절 경계 이벤트)는 2단계 백로그의 첫 코어 이슈로 둡니다.
