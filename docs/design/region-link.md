# 지역 연결 설계

- 상태: 초안 v0.1 (2026-11-27, 기획). 구현은 3단계 이후.
- 결정: [ADR 0006](../adr/0006-region-link.md) · 근거: [research-log.md](research-log.md#region-link)

## 한 줄 정의

각자 자기 동네를 돌리고, **계절마다 이웃 동네와 경계를 넘는 흐름을 주고받습니다.** 평택 플레이어 옆에 오산·안성·천안 플레이어가 붙는 식입니다.

## 구조

```
[내 컴퓨터: 평택 코어] ──계절 끝: 경계 출력 + 상태 해시──▶ [지역 게시판 서버]
         ▲                                                    │ 보관·중계만 함
         └──────────다음 계절 시작: 이웃들의 경계 입력─────────┘
                                                              │
                         [이웃 플레이어 컴퓨터] 또는 [가상 이웃 모델]
```

- 서버는 시뮬을 돌리지 않습니다. 각 동네의 계절별 경계 출력 묶음을 보관하고 이웃에게 나눠 줍니다. 검증 시에만 표본을 다시 돌립니다.
- 서버가 없거나 끊기면 가상 이웃이 모든 포트를 채웁니다. 게임은 그대로 진행됩니다.
- 이웃이 늦으면 기다리지 않습니다. 그 이웃의 가장 최근 값이나 가상 이웃 값을 씁니다.

## 경계 포트

경계 포트는 동네 테두리에 놓인 **관문(gate)** 하나와, 그곳을 지나는 **흐름 종류** 하나의 조합입니다.

| 흐름 | 관문 | 단위 (계절 합계·평균) | 시작 단계 |
| --- | --- | --- | --- |
| 통근·통학 | 경계 도로·철도역 | 방향별 인원/일, 시간대 분포 | 1단계부터 가상 이웃으로 |
| 화물 | 경계 도로 | 방향별 화물차/일 | 2단계 |
| 상품 수출입 | 동네 전체 | 품목군별 금액 | 2단계(경제) |
| 인구 이동 | 동네 전체 | 가구 유형별 전입·전출 | 2단계 |
| 하천 | 하천 유입·유출 지점 | 첨두 유량, 수질 등급 | 2단계(기후) |
| 전력·물 | 송전선·관로 | 공급 가능량, 사용량 | 3단계 이후 |
| 세금·협약 | 동네 전체 | 공동 투자 분담금 | 3단계 이후 |

### 코어 API 초안 (구현 담당이 다듬어도 됨)

| 함수 | 설명 |
| --- | --- |
| `boundary_gates()` | 맵 패키지에서 읽은 관문 목록 (id, 위치, 종류) |
| `set_boundary_inputs(period, inputs)` | 이번 계절에 이웃이 보낸 값. 코어는 이것을 명령처럼 기록 |
| `boundary_outputs(period)` | 계절이 끝난 뒤 내 동네가 이웃에게 보내는 값 |
| `state_hash()` | 결정론 상태의 해시. 검증·리플레이·테스트용 |

- 경계 입력은 명령 기록(`submit`)과 같은 로그에 들어갑니다. 그래서 "맵 + 시드 + 명령 로그"만 있으면 어떤 계절이든 다시 돌릴 수 있습니다.
- 값은 모두 정수입니다(인원, 대수, 원, 리터). 소수가 필요하면 고정 배율(예: ×1000) 정수로 둡니다.

## 결정론 규칙 (지금부터 코어에 적용)

1. 시뮬 상태와 경계 출력에 영향을 주는 계산은 **정수 또는 고정소수점**으로 합니다. `f32`/`f64`는 클라이언트 연출과 통계 표시에만 씁니다.
2. 삼각함수·제곱근 같은 초월 함수는 시뮬 상태에 쓰지 않습니다. 꼭 필요하면 정수 근사 표를 씁니다.
3. 난수는 시드를 고정한 하위 시스템별 생성기(예: 교통, 기후 따로)를 쓰고, 생성기 알고리즘을 코어 안에 고정합니다(외부 크레이트 버전 변경으로 결과가 바뀌지 않게).
4. 반복 순서가 정해지지 않은 자료구조(`HashMap` 순회 등)의 순서에 결과가 의존하면 안 됩니다. `BTreeMap`이나 id 순 정렬을 씁니다.
5. 멀티스레드 계산은 결과를 고정 순서로 합칩니다.
6. CI에서 같은 시나리오를 Linux·Windows·macOS로 돌려 `state_hash()`가 같은지 확인합니다.

## 가상 이웃

- 혼자 할 때 쓰는 기본 이웃입니다. 공공 통계(시군구 간 통근 통계, 하천 유역)를 바탕으로 한 단순 규칙 모델입니다. 데이터 출처는 2단계에서 조사합니다(조사 과제).
- 내 정책에 약하게 반응합니다. 예: 내가 세금을 크게 내리면 가상 이웃에서 전입이 조금 늘어남.
- 실제 플레이어가 오프라인이 되면 그 플레이어의 최근 경향을 이어받아 가상 이웃이 대신합니다.

## 조작 방지

- 계절마다 `경계 출력 + state_hash + 명령 로그 해시`를 제출합니다.
- 서버가 무작위 표본(그리고 순위표 상위권 전부)을 같은 코어 버전으로 다시 돌려 출력이 같은지 봅니다.
- 다르면 그 계절 출력은 이웃에게 전달하지 않고 가상 이웃 값으로 바꿉니다.
- 순위표가 없는 친구 간 사적 연결은 검증을 끌 수 있습니다.

## 재미 포인트 (기획 가설, 플레이 테스트로 확인할 것)

1. **진짜 이웃 라이벌:** 실제 옆 동네가 상대라 결과 비교 자체가 이야기가 됩니다.
2. **정책의 파급:** 내 세금·교통 정책이 옆 동네 전입·통근을 바꾸고, AI 시민 뉴스에 "평택으로 떠나는 사람들" 같은 기사가 뜹니다.
3. **협상과 외교:** 광역버스 공동 투자, 쓰레기 처리장 위치, 하천 관리 협약을 이웃과 합의합니다.
4. **공동 위기:** 집중호우 때 상류 동네의 불투수 면적이 하류 침수를 키웁니다. 기후 시스템(ADR 0003)이 협력의 이유가 됩니다.
5. **광역 순위:** 지역별 통근 시간·폭염 피해·행복도 순위와 시즌 이벤트.
6. **실제와 비교:** "내 정책 vs 실제 평택시" 결과 비교. 교육·시민 참여 용도.

## 열린 문제

- 이웃 둘이 서로 다른 코어 버전일 때 처리(계절 단위 호환 버전 범위).
- 관문 위치를 이웃 동네끼리 맞추는 방법(같은 OSM 도로를 양쪽 맵 패키지가 같은 id로 인식).
- 서버 운영 주체와 비용(커뮤니티 서버 여러 개를 허용할지).
- 실제 지명 사용에 따른 콘텐츠 관리 정책.
